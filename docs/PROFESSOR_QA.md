# Likely questions and technically correct answers

**Why Simulated Annealing?** The problem is integer, non-convex (minimum viability thresholds) and multi-constraint, so Lagrangean/DP/greedy exactness results for the convex single-constraint case do not apply. SA is gradient-free and handles discontinuous objectives.

**Is SA guaranteed to find the optimum?** No. Hajek's guarantee needs logarithmic cooling, which is impractically slow. Our geometric cooling is a heuristic; quality is measured empirically (30 runs, gap vs exact on small instances).

**How do you handle constraints?** Penalty in the energy: λ·Σ max(0,(usage−R)/R). The viability domain {0}∪[L,U] is enforced by construction (snapping rule). Only *feasible* states can become the reported best, so output is always feasible.

**Why λ = 10·max v?** A starting rule: a 10 % over-use of one resource costs about as much as the best project is worth. It is an initial test value, not proven optimal; you can change it on the SA page. A limitation: a penalty that is linear in relative violation could in principle tempt SA into small violations, which is why we keep the best feasible state separately.

**Are T₀=50, α=0.95 optimal?** No – they are initial test values; the sensitivity page measures their effect and reports only the “best observed configuration for this experiment”.

**What is ΔE and why accept worse moves?** ΔE = E(x′)−E(x). Worse moves are accepted with p = exp(−ΔE/T) so the search can leave local optima; as T falls the search becomes greedy.

**How many iterations?** levels = ⌈ln(Tmin/T0)/ln α⌉ = 167 for the defaults; × chain 100 = 16,700 evaluations.

**How is the exact optimum computed, and when?** Depth-first enumeration over {0,L..U} per project with pruning when a capacity is exceeded (valid because a_ij ≥ 0). Only when the raw space ∏(U−L+2) ≤ 2,000,000; otherwise the app shows “Exact optimum not computed for this instance.” and never invents a gap.

**Is the random baseline fair?** By default it gets as many random feasible samples as SA has energy evaluations (best-of-N).

**What does greedy do and why can it lose?** It repeatedly takes the step with the highest utility gain per normalised resource cost. It never undoes a step, so it can get stuck in a locally good but globally worse allocation, and cannot trade one project off against another.

**What if SA loses to greedy?** The app reports it honestly; the narrative text switches to “below”. On some instances a good greedy is hard to beat.

**Reproducibility?** Python `random.Random(seed)` drives SA; run r of an experiment uses seed base+r; random baseline uses seed+7,000,000. Same dataset + seed ⇒ identical allocations (runtime varies by machine).

**Why is the SA core in plain Python, not NumPy?** Each move changes ≤2 projects, so incremental O(m) updates on Python lists are faster than NumPy calls; NumPy is used for statistics/histograms. Energies are resynchronised from scratch after every chain to avoid floating-point drift.

**Why is SA runtime tiny?** 16,700 incremental evaluations on a small instance take tens of milliseconds; the live demo adds an adjustable pause for visibility which is excluded from the reported runtime.

**Are the data real?** No – documented synthetic university-portfolio parameters (as stated in Review 1's limitations). `large` is generated by a seeded generator from category profiles.
